# ActyTrack V3 Build Spec ## Overview Complete rewrite of ActyTrack with new data model, new stage, and unified workflows. Cloud-only persistence, hardcoded JSONBin ID: 69c0230aaa77b81da90aee10 ## Stages (new order, new "Maintain" stage) Inspect → Monitor → Maintain → Purchase → Install - All stages get identical done flows - "Starting Stage" label renamed to just "Stage" ## Stage Config - Inspect: color #d68910, icon ⊙ - Monitor: color #3a7fc1, icon ◉ - Maintain: color #c0392b, icon ⚙ (new) - Purchase: color #c9a84c, icon ◎ - Install: color #2ea84a, icon ◈ ## Task Types Maintenance, Repair, Modification (unchanged) ## Priority Urgent, This Week, Upcoming, Long-term - Tapping escalates (sooner, not later) - Priority boxes at top act as filters (tap to show only that level) - On load, auto-open the FIRST priority tier (in order Urgent → This Week → Upcoming → Long-term) that has at least one task. If Urgent has tasks, only Urgent opens. If Urgent is empty but This Week has tasks, This Week opens instead. And so on. All other tiers start collapsed. ## Parts on Task Cards - Every task card has an editable parts list - Parts are objects: { id, name, cost, status } - Status: "tobuy" → "ordered" → "installed" - Cost auto-formats to $0.00 with dollar sign - Inline editing: tap part name to edit, tap to add new part, X to remove - Ordered parts show checked off and moved to bottom of list on card - Parts auto-populate the Shopping List tab ## Shopping List Tab (single source — task card parts only) - Shows parts from all task cards (grouped by to-buy and ordered) - No standalone "Add Shopping List Item" — everything comes through task cards - Even dream/wishlist purchases become a long-term task with parts on it - The + button only creates Work Queue tasks (no shopping list option) - When adding parts during task creation, they auto-appear on the Shopping List tab - When a part is checked as ordered in shopping list, it updates the task card - When a part is received/installed, option to log to service history and/or parts list ## Task Fields Every task has: - title, notes, stage, type, priority - mileage: editable, auto-formats to "XX,XXX km". For recurring tasks, this IS the "due at" value - date: editable date field. For recurring tasks, this IS the "due by" value. For non-recurring tasks, can be a target date or empty - parts (linked from purchases by taskId) - recurring (optional): stores ONLY the interval — { kmInterval: 5000, monthsInterval: 6 }. No dueAtKm or dueByDate in here — those live in the task's own mileage/date fields ## Recurring Task Lifecycle - Collapsed card shows "due @ 93,734 km" / "due Sep 2026" — reads from task.mileage / task.date - Auto-escalation checks task.mileage and task.date against current odo / today's date - When completing a recurring task: - Done flow pre-fills mileage/date from the task's fields - Logs to service history with those values - New task created with: - mileage = completed mileage + kmInterval (e.g. 88,937 + 5,000 = 93,937 km) - date = completion date + monthsInterval (e.g. today + 6 months) - recurring = just the interval { kmInterval, monthsInterval } (unchanged) - priority = "longterm" (will auto-escalate as due date approaches) ## Date Field - Every task card has an editable date field next to mileage - Displayed on collapsed cards alongside mileage - For recurring tasks: this is when the task is due - For non-recurring tasks: optional target/planned date - Editable inline like mileage - Date input (defaults to today, editable for backdating completions — carries to service log and parts list installed date) - Mileage input (for recurring tasks, pre-filled from task's mileage/due field) - Note input (auto-resize textarea) - Repeat? (km/months/both/no) - Two toggles: "Service Log ✓" and "Parts List ✓" — can pick none, one, other, or both - If Parts List is toggled on: show category picker - Complete button resolves the task - Date carries through to service log entry and parts list installed date ## Stage-specific promotion flows (before the done/resolve screen) - Monitor done: → Inspect, → Maintain, → Purchase, → Install, or Resolve - Inspect done: Passed (resolve), → Maintain, → Purchase, → Install - Maintain done: straight to resolve/log screen - Purchase done: → Install, or Resolve - Install done: straight to resolve/log screen ## Task Creation (+ button) - Only creates Work Queue tasks (no separate shopping list option) - Fields: title, notes, stage, type, priority, parts - Parts can be added during creation with name + cost fields - Parts added here auto-appear on the Shopping List tab - This is the ONLY way to add items to the shopping list ## Service Log - Parts stored as strings - All fields editable with [edit] links (title, date, mileage, notes, parts) - Timeline rail display with category colors - Filter by category ## Mileage - Every mileage input auto-formats to "XX,XXX km" on blur - Updating mileage anywhere propagates to vehicleOdo and triggers auto-escalation ## Vehicle Info Tab - Vehicle specs (static) - Current odometer (editable) - Licensing & registration - Parts List (expandable, filterable by category, editable) - Shops & Contacts (Tagami Auto, JDM Imports) - Previous Owner Notes - Sync status - Export/Import backup buttons ## Filter Buttons - Stage and Type filters are toggles (no "All" button) - Each has its own color when active, muted when off - Gap between buttons so they read as individual toggles - At least one must stay on ## UX Features to Preserve - Auto-resize textareas (defined outside component to prevent remount) - Scroll follows task when priority changes - Collapse from bottom (3+ tasks in a group) - Scroll to top at bottom of work queue - Inline pickers for priority/stage/type (tap to open options, tap to select) - Loading screen while cloud data loads - Delete confirmation on all deletable items ## Visual Theme - Current dark theme for now (Concept C workshop manual reskin deferred) - Courier New monospace font throughout - Bump overall sizing up a notch from the current build for readability: - Card titles: ~15-16px (up from 13px) - Body/notes text: ~13-14px (up from 12px) - Labels/badges: ~10-11px (up from 9px) - Buttons: larger tap targets, more padding (~8-10px vertical instead of 5-6px) - Priority count numbers: larger (~24-26px) - More breathing room between elements generally (increase gaps/margins slightly) - Icons and checkboxes sized up proportionally - Goal: easier to read and tap at a glance, especially outdoors/in the garage ## Persistence - Loading screen until cloud data arrives ## Data Migration (CRITICAL — do not lose existing data) - The live JSONBin (id 69c0230aaa77b81da90aee10) already has real data in the CURRENT v8 shape (see uploaded HTML for exact current schema: tasks with string/object parts, purchases array, recurring with dueAtKm/dueByDate, stages inspect/monitor/tuneup/purchase/install) - The new build MUST include a migrate() function that runs on cloud load and reshapes old data into the new v3 model: - Old task.parts (whether string or old-object format) → new purchases entries linked by taskId - Old recurring.dueAtKm / recurring.dueByDate → move those values into the task's own mileage/date fields; recurring keeps only kmInterval/monthsInterval - Old stage names (e.g. "tuneup") → map to whatever the new stage list ends up being - Tasks without a date field → date defaults to null/empty, not an error - This must be non-destructive: after migration, all existing tasks, service log entries, purchases, and parts list items should still be present and usable - Uploading the new HTML to GitHub does NOT wipe data — the bin ID is hardcoded and persists independently of the code. Migration just reshapes what's already there the first time the new code reads it.
